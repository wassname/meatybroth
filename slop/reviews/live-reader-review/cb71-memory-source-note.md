# cb71 memory-source note

Read-only source inspection of `cb71d87` after a reported 1.293 GiB Rust RSS with about 157 MiB host memory available. This identifies allocation-capable paths; it does **not** establish which pages were resident in that process or a cause of the measured RSS.

1. **Each HTTP request creates its own SQLite memory budget, with no app-level request limit.** `src/main.rs:681-690` opens a read-only connection inside `spawn_blocking` and sets `cache_size=-65_536` (64 MiB), `mmap_size=268_435_456` (256 MiB), and `temp_store=MEMORY`. `src/embed.rs:340-347` sets the same cache/mmap values for each embedding helper connection. These are ceilings/configuration, not automatically resident memory; however, concurrent reader/embedding connections can each use page-cache and memory temporary storage. The source has no semaphore around HTTP `spawn_blocking` work. This is the strongest directly actionable memory-pressure candidate, but it cannot by itself attribute 1.293 GiB without a process map or connection count.

2. **Meaning/Similar performs a full selected-space vector scan in process.** `src/embed.rs:1382-1419` collects every 30-day eligible `(event_id, vector BLOB)` into a `Vec`, then allocates a second scored vector and sorts it. At the status-reported 10,012 cached Titan 512-d vectors, the float payload alone is about 19.6 MiB (10,012 × 512 × 4), before BLOB/Vec/ID allocations and sorting. This is a bounded-by-corpus request allocation, not an explanation for 1.293 GiB alone. The immutable local 8,136-vector snapshot measured 414 ms nearest-stage time before `cb71`; its candidate Similar total was 0.992 s, but that benchmark did not record RSS ([`2026-09-14_responsive-reader-snapshot-benchmark.log`](../../verification/2026-09-14_responsive-reader-snapshot-benchmark.log)).

3. **`/status` recomputes broad eligibility and accounting rather than reading a small status cache.** `src/main.rs:623-677` calls `queries::count` and `embed::cache_status`. `src/embed.rs:1009-1048` materializes eligible 30-day IDs/receive times, then runs correlated counts/anti-joins for each embedding space. Eligibility expands `posts` → `reader_post_events` → events and policy/moderation JSON predicates (`src/posts.sql:1-43`; `src/queries.rs:59-66`). Under `temp_store=MEMORY`, this is a credible contributor to the observed 22.7-second compressed-status TTFB and temporary memory pressure, but not proven as the RSS cause.

`cluster_topics` also collects every vector **and full event content** (`src/embed.rs:1137-1158`), then retains clustering copies. It is a whole-corpus allocation worth keeping out of the live server. At `cb71`, normal continuous `collect::run` does not call it; source calls it only in `MEATYBROTH_EMBED_ONLY` backfill and `MEATYBROTH_RECLUSTER_ONLY` (`src/main.rs:834-911`). Do not attribute current continuous-server RSS to clustering without checking its actual launch environment.

The post-`cb71` reader fix already bound card hydration to ranked IDs (`queries::eligible_map_for` at `src/queries.rs:252-282`), replacing the earlier global card preparation visible in the local benchmark. I found no comparably obvious whole-corpus card-hydration allocation in the normal New/Similar page path.
